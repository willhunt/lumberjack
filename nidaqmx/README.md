# nidaqmx

Safe wrappers over the National Instruments DAQmx driver.

Enough of it to read analog input from a USB-6001, which we keep for legacy
reasons. New work goes to Pico.

## What you need, and what you do not

**Nothing, to build this.** There is no `build.rs`, no `links` key and no
`NIDAQmx.lib`. The only dependency is `libloading`.

The driver is looked up at run time from `nicaiu.dll`, which the NI-DAQmx
runtime installs into `System32`. So the workspace compiles and runs on a
machine with no NI software at all, and only somebody actually reading NI
hardware needs the runtime. A driver that is not there fails at `load()` saying
what it looked for, rather than failing to link.

Regenerating the bindings is the only thing that wants more: the header, from
NI-DAQmx **Support for C**, and LLVM for bindgen. That happens once per driver
release, not once per build.

## Why not the published crate

[`daqmx-rs`](https://github.com/WiresmithTech/daqmx-rs) is MIT, well organised,
and worth reading for how DAQmx is shaped. It is not depended on because its
`ni-daqmx-sys` emits

```
cargo:rustc-link-lib=nidaqmx
```

so building against it wants `NIDAQmx.lib`, and therefore the NI C development
component, on every machine that compiles this — whether or not anyone there
owns NI hardware. That is the cost we are avoiding, and unlike its old
build-time bindgen it cannot be fixed by regenerating.

## How the bindings work

`src/raw/` holds bindings generated by bindgen and **committed to the
repository**, rather than generated during the build, for the same reasons
`picolog` does it.

They use bindgen's `--dynamic-loading`, so each function is a pointer looked up
by name at run time rather than a link-time symbol.

Only the functions actually called are bound. `NIDAQmx.h` declares **3,384**
functions, most of them property accessors, and allowlisting all of them
produced 2.1 MB of bindings and as many symbol lookups on load. The allowlist
below covers analog input; extend it when something needs more.

## Regenerating

Generated from **NI-DAQmx 2026 Q3**. Only needed when that changes.

```powershell
$env:LIBCLANG_PATH = "C:\Program Files\LLVM\bin"
bindgen "C:/Program Files (x86)/National Instruments/Shared/ExternalCompilerSupport/C/include/NIDAQmx.h" `
  --dynamic-loading NiDaqmx `
  --allowlist-function "DAQmx(CreateTask|ClearTask|StartTask|StopTask|CreateAIVoltageChan|CfgSampClkTiming|ReadAnalogF64|ReadAnalogScalarF64|WaitUntilTaskDone|GetExtendedErrorInfo|GetErrorString|GetSysDevNames|GetDevProductType|GetDevSerialNum|GetDevAIPhysicalChans|SelfTestDevice|ResetDevice)" `
  --allowlist-var "DAQmx_Val_(Cfg_Default|Diff|RSE|NRSE|PseudoDiff|Volts|Rising|Falling|FiniteSamps|ContSamps|GroupByChannel|GroupByScanNumber|WaitInfinitely|Auto)" `
  --allowlist-type "(TaskHandle|int32|uInt32|float64|bool32)" `
  --no-layout-tests `
  -o src/raw/nidaqmx.rs
```

Then put back the `//!` lines and the two `#![allow(...)]` at the top of the
file, which bindgen replaces with its own header.

Record which DAQmx release it came from, above. NI do not follow semver, so
knowing which header the bindings describe is the only way to tell whether a
difference is a bug or a version.

## Checking a device

```cmd
cargo run -p nidaqmx --example probe_devices
```

```
Driver loaded.

  Dev1  USB-6001  simulated
      8 analog inputs
          Dev1/ai0
          Dev1/ai1
          ...
```

DAQmx addresses channels by device name, as in `Dev1/ai0`, so a config has to
hold the name NI MAX gave the hardware. This asks the driver rather than
guessing.

A **simulated** device, made in MAX, appears here exactly as a real one does,
which is what makes it useful to develop against. It is still NI's model of the
hardware rather than the hardware: take what it accepts as provisional until the
real unit has been asked the same question.
